# LSM 樹（Log-Structured Merge Tree）

LSM 樹是為了**寫入密集**工作負載而設計的資料結構，廣泛用於 NoSQL 與資料庫引擎。它把「隨機寫入」轉化為精心安排的「循序寫入」，因此對旋轉式硬碟和 SSD 都很友善。

## 為什麼傳統 B 樹在寫入上吃虧

[B-Tree](B樹.md) 對「就地更新」很擅長，但每次寫入都可能要改動樹的多個節點並隨機尋軌。在高頻寫入情境下，隨機的磁碟 I/O 成為瓶頸。LSM 選擇了另一條路：**不就地更新，而是把變更先堆起來，之後再合併**。

## LSM 的組成

一張 LSM 樹由一連串「層」構成，由新到舊：

1. **Memtable（記憶體表）**：所有寫入先進入這個常駐記憶體、通常有序的結構（例如紅黑樹或跳過表）。寫入到此就回覆成功——極快。
2. **WAL（Write-Ahead Log）**：在寫入 memtable 前，先把操作循序寫入這個 append-only 日誌。如此若系統當機，可由 WAL 重放恢復 memtable 內容。這是「先把建置鏡頭放進來再進表」的耐久性保證。
3. **SSTable（Sorted String Table）**：當 memtable 滿了，就把有序內容**整批、循序地**刷成一個磁碟上的有序檔案，並清空 memtable 重建。SSTable 彼此有序且不可變。

## 合併（Compaction）

因為 SSTable 會愈積愈多、且各層之間可能有重複的鍵，LSM 定期做**合併（compaction）**：把相鄰的 SSTable 讀出、合併排序、寫成更大的 SSTable，順便丟棄被覆蓋/刪除的舊版本。這讓資料維持相對有序、控制檔案數量、回收空間。

## 讀取如何進行

讀一個鍵會**從新往舊**依序檢查：

1. 先查 memtable。
2. 再依序查各層 SSTable。

若表層數多且沒有輔助，讀取可能要翻遍很多檔案。為了加速，LSM 常搭配：

- **Bloom Filter**：先快速判斷「這個鍵**肯定不在**這個 SSTable」，跳過無謂的檔案查詢。
- **檔案內的索引**與稀疏樣本：快速定位有序檔案內的位置。

## 寫入 vs 讀取 vs 空間的權衡

- **寫入極快**：隨機寫 → 記憶體寫 + 循序 WAL。
- **讀取較慢**：可能跨多層查詢，需 Bloom Filter 救濟。
- **空間放大**：同一鍵可能有數份版本，需靠合併回收。

LSM 因此在「寫入頻繁」的場景勝出，但「讀取大量／即時一致」的場景，傳統 B 樹仍占優——所以許多引擎混合兩種結構各取所長。
